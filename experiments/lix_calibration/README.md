# LIX threshold calibration

What long-word threshold makes LIX behave sensibly in Hungarian? Answer it empirically,
from a token-weighted word-length distribution, rather than by guessing.

The method is **equipercentile matching**: find the Hungarian threshold whose long-word
share is closest to the share Björnsson's `>6` picks out in a Germanic reference. That
preserves what the second LIX term *means* — the longest X% of running words — instead of
preserving the literal 6.

Two thresholds ship, because a threshold is calibrated against a way of counting letters:
`hu` for the default character count and `hu-letters` for
`saphes.hungarian.hungarian_letter_count`. Both come out at 8; the share of running words
behind that 8 differs, so each has its own agreement panel measured under its own policy.

Outputs, all committed:

- `findings.md` — the writeup, generated by `scripts/run.py`
- `validation.md` — the end-to-end check, generated by `scripts/validate_b.py`
- `results/lix_calibration.json` — full provenance, every curve at every threshold
- `../../src/saphes/datasets/_lix_calibration.py` — the literal the package ships

## How to run

All commands run from the repo root.

```bash
# Smoke test first (~2.8 MB Hungarian + the Leipzig pair, about a minute)
uv run python experiments/lix_calibration/scripts/download_data.py --smoke-test
uv run python experiments/lix_calibration/scripts/run.py --smoke-test

# Full run (~115 MB frequency list; the run itself takes about four minutes)
uv run python experiments/lix_calibration/scripts/download_data.py
uv run python experiments/lix_calibration/scripts/run.py

# End-to-end validation on running text (~370 MB corpus part)
uv run python experiments/lix_calibration/scripts/download_data.py --with-corpus-part
uv run python experiments/lix_calibration/scripts/validate_b.py
```

Downloads are cached in `data/` (gitignored) and skipped if already present. The smoke run
writes only the JSON; it does not regenerate the shipped literal or `findings.md`, because
the truncated word list is not what the package should ship.

## Scripts

| script | role |
|---|---|
| `download_data.py` | Step 1. Streams the corpora, verifies sizes, records sha256 in `data/manifest.json`. |
| `freqlist.py` | Reader for the MOKK frequency lists. Where the correctness landmines are. |
| `leipzig.py` | Reader for Leipzig `*_1M.tar.gz` word lists. |
| `running_text.py` | Reader for the Leipzig `-sentences.txt` member, and LIX on running text. |
| `corpus_part.py` | Reader for a Webcorpus crawl part — the only source with sentence boundaries. |
| `run.py` | Step 2. Builds the curves, matches, runs the sensitivity panel, writes the artifacts. |
| `validate_b.py` | Step 3. Real *A*, *B* and *C* from running text. |
| `utils.py` | `log`, `require_file`, shared paths. |

The pure analysis — `length_curve`, `match_threshold`, `collapse_digraphs`, and the letter
count in `saphes.hungarian` — lives in the package, not here. It ships with the package because the caveats say users
must recompute on their own register, and it is data-free so its doctests run in CI.

## The four things that decide whether this is right

1. **Token-weighted, never type-weighted.** The frequency file is a *type* list; rare types
   are long, so a mean length over types runs far above the mean in running text. Get this
   wrong and the number is inflated *and still looks plausible*. `length_curve` takes a
   frequency mapping and never a token list, so there is no way to call it that forgets.
2. **Use the 4% stratum**, not the full-corpus column. The 4% stratum has fewer mistakes
   than an average print document; the full column carries the crawl's junk.
3. **Strip the trailing asterisk, then casefold, then filter — in that order.** Capitalised
   forms are marked `A*`, `Az*`, `És*`; `A*` alone is 8.9M tokens in the 4% stratum. A
   naive alphabet filter discards them all, and they are overwhelmingly *short* function
   words, so the mean length is biased upward. Then accumulate with `+=`: after stripping,
   `A` and `A*` both map to `a`, and a dict assignment would keep only the last.
4. **Decode as ISO-8859-2.** Reading the file as UTF-8 corrupts `ő` and `ű` — precisely the
   characters that distinguish Hungarian, and a direct hit on the length counts.

## Regression anchors

`run.py` asserts a set of numbers measured by hand before the pipeline existed, and exits
non-zero rather than publishing different ones. If you change a reader, expect these to
fire — and work out which behaviour is correct before you update them.

One has already been updated once, for a good reason. The exploratory scripts applied the
minimum-frequency filter *per row*, before merging casing variants. The pipeline applies it
*after* merging, so a type is judged on its total across all variants — dropping `Och` at
frequency 3 before merging it into `och` at frequency 100,000 is plainly wrong. That
single change accounts for the whole difference (Swedish `>6` moved 0.2545 → 0.2565).

## Data sources

- **Hungarian Webcorpus** (MOKK/BME) — <http://mokk.bme.hu/resources/webcorpus/>.
  Permissive Open Content, but **citation is required**: Halácsy et al. (LREC 2004) and
  Kornai et al. (Web as Corpus, ACL 2006).
- **Leipzig Corpora Collection** — `swe_news_2022_1M` supplies the reference share,
  `hun_news_2022_1M` cross-checks the Webcorpus under identical methodology. Cite Goldhahn
  et al. (LREC 2012).

The `web2-4p-*.tar.gz` crawl parts are ~370 MB each; **one is plenty**, and it is needed
only for the sentence-count validation, since no frequency dictionary can supply *B*.
